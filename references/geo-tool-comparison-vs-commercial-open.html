ACMS GEO 工具能力 — 商业 & 开源细项对比

基于 ACMS v0.45（2026-09-06 实测）与公开文档 / 代码审计数据
数据来源：ACMS 前端代码（client/js/views/geo-dashboard.js / geo-tools）、后端服务（server/services/geo-*）、参考文档（docs/geo-app-redesign-architecture.md、references/oneglanse-final-report-2026-09-06.md）、开源项目（OneGlanse / GEORank / TagSpaces）。对比对象：开源 = OneGlanse、GEORank（Elmo）、TagSpaces、TOAST UI Image Editor；商业/服务 = DeepSeek（LLM 引擎）、Perplexity（搜索引擎）、GEOVisibilityTool（借鉴卡片模式）。
结论先说（多多拍板风格）：ACMS GEO 在“结构化数据生成（JSON-LD / Schema）+ 内容缺口分析（content gap）+ 品牌感知 LLM 评审 + 国内双引擎（豆包/元宝）DOM 追踪”四个维度上已形成闭环，超过单一开源工具（OneGlanse 只做可见性分析、GEORank 只做评分、TagSpaces 只做文件浏览）；但在“原生联网搜索引擎接入（native search）”和“多引擎实时并发监控”上仍落后 Perplexity / DeepSeek 原生能力。当前 v0.45 的核心差距是：GEO 工具（JSON-LD / 标题 / KB）是 LLM 单次调用生成，非真实搜索引擎数据驱动；而 OneGlanse / GEORank 的分析结果直接来自引擎响应数据（更真实但无生成能力）。这是“生成型”与“监测型”的根本差异，不是简单功能缺失。

关键差距总结（按多多拍板风格）

1. 生成型 vs 监测型的本质差异
ACMS GEO 工具（JSON-LD / 标题 / KB / 智能推荐 / 投放策略）全部是 LLM 生成型（基于品牌 brief 和已有数据生成结构化输出）；OneGlanse / GEORank 是 监测分析型（基于真实引擎响应数据计算指标）。这不是功能缺失，而是产品定位差异：ACMS 更偏向“从分析到执行”的闭环工具（生成 + 投放），OneGlanse 更偏向“纯可见性监控”。

2. 国内引擎适配（豆包/元宝）的最大差距
`doubao.js` / `yuanbao.js` 标记为 `v0.1 placeholder`（需要真实浏览器自动化 + 登录态）。`capabilities` 已正确标注（`search: dom`、`maxConcurrent: 1`、`timeoutMs: 120000`），但实际 DOM 选择器和登录流程未实现。这是从“架构就绪”到“生产可用”的最大技术差距（约需 1-2 周真实选择器调试）。相比之下，DeepSeek / Perplexity 通过官方 API 已可直接使用，无需 DOM 驱动。

3. 数据持久化的架构差异
ACMS 使用 SQLite（`geo-store.js` 的 `collection()` API），OneGlanse 使用 PostgreSQL。这对单用户/本地部署有利（无服务器依赖），但对多用户高并发场景不利（SQLite 锁机制限制并发写入）。如果 ACMS 未来需要支持多品牌并发分析（如 agency 场景），需要考虑从 SQLite 迁移到 PostgreSQL（参考 OneGlanse 架构）。

4. 前端布局的设计哲学（借鉴 oneglanse-v038 卡片模式）
`geo-v038-card`（竞品共现 + 感知分析）的设计完全借鉴 OneGlanse 的 `BrandAnalysisResult` 卡片布局（数据字段命名一致、CSS 类名对齐 `.geo-v038-*`），这说明 ACMS 在“可借鉴的界面模式”上与 OneGlanse 高度一致。差异在于：ACMS 将这些卡片集成到现有 `geo-dashboard` 流程中（而不是独立页面），并增加了 `data-tip` 悬停说明（符合多多“每个界面指标要有悬停说明”的要求）。
